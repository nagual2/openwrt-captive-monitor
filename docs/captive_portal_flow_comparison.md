## Analysis of Failure

Despite NoJS successfully creating a session and obtaining an `apiSessionId`, the final login step fails with **Access denied**.

**Key Observation:**
The `apiSessionId` obtained by NoJS (`34kn0s3trb04dgkhp6t5h6l4r7`) differs from the one obtained by Selenium (`f1q7lolc2avrd7kaml9e2n53m2`). This confirms that the server generates unique session IDs for each request.

The failure likely stems from one of the following:
1.  **Token Signature/Timestamp mismatch:** The `wbsApiAuthToken` used by NoJS might have a slightly different timestamp or structure than what the server expects for the *current* connection context, even if the structure looks correct.
2.  **Authorization Token Type Mismatch (New):** The server expects `authorization=session=<PHPSESSID>` for `/wbs/api/v1/login/free/`. In the current NoJS flow, `authorization` is being sent as `session=<apiSessionId>`, which the server rejects with `code=700` ("Empty or illegal token"). Selenium uses the browser-managed `PHPSESSID` cookie and the API payload aligns with it. This is the primary divergence causing the 403.
3.  **Hidden Browser Headers/Fingerprint:** The browser sends headers like `Sec-ch-ua`, `Origin`, `Referer` which NoJS tries to mimic, but subtle differences (TLS fingerprint, order of headers) might trigger anti-bot protection.
4.  **Additional XHRs:** The browser might be making other hidden requests (analytics, logging) that "warm up" the session or register it as valid before the final login click.

## 6. Remediation Plan

- Гарантировать `PHPSESSID` перед `login/free` (предзапросы: `/registration-free`, `/wbs/authenticate-me/`, `payment-return-proxy.php`).
- Использовать `authorization=session=<PHPSESSID>` и передавать `apiSessionId` отдельно в поле `apiSessionId` (уже реализовано; всё ещё 403).
- Держать `paymentReturnProxyUrl` непустым (реализовано; совпадает с Selenium).
- Перепроверить происхождение `wbsApiAuthToken`: восстановление должно использовать актуальный `himalaya-site-ident` и соответствующий hash‑суффикс; исключить устаревшие/статические значения.
- Свести согласие к минимальному набору полей, повторяющему Selenium (избежать лишних параметров, проверить регистр ключей camelCase/snack_case).
- Диагностировать заголовки/отпечаток TLS: сравнить `User-Agent`, `Origin`, `Referer`, `sec-ch-ua*` и порядок заголовков, при необходимости воспроизвести поведение браузера для XHR.
