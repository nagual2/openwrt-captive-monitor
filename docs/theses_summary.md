# Сводный перечень тезисов о работе скриптов и сред

В данном документе собраны все ключевые установки и правила, выработанные в ходе диалогов, касающиеся настройки окружения, запуска скриптов и методологии разработки в проекте `openwrt-captive-monitor`.

## 1. Рабочая среда (WSL vs Windows)
- **Основная ОС:** Разработка ведется на Windows в директории `c:\git\openwrt-captive-monitor`.
- **Разделение полномочий:**
    - **Windows:** Нативно запускаются Git, GitHub CLI (gh), работа с файлами в IDE.
    - **WSL:** Используется для выполнения ВСЕХ скриптов (Python, Shell), SSH-подключений к роутерам, сборки (make), сетевых утилит и работы с SDK.
- **Подключение:** Для работы в Trae/VS Code рекомендуется расширение `Open Remote - WSL` для прямого доступа к Linux-окружению.
- **Сетевые хосты:** SSH к роутерам осуществляется через `wsl ssh`. Хосты должны быть прописаны в `/etc/hosts` WSL:
    - `192.168.1.1 dev-openwrt`
    - `192.168.x.x prod-openwrt`

## 2. Запуск скриптов и инструментов
- **Строгое правило:** Любой Python или Shell скрипт запускается только через префикс `wsl` (если запуск идет из Windows-терминала) или непосредственно внутри WSL.
- **Инструментарий:**
    - Линтеры и типизация: `Ruff` и `MyPy` запускаются через WSL.
    - Сетевая диагностика: `mitmproxy`, `HTTPie`, `curl` устанавливаются и работают только в WSL.
    - CLI-утилиты: Рекомендуется установка через `pipx` для изоляции зависимостей.
- **Анализ кода:** Для экономии контекста используются индексы:
    - Символьная карта: `.cache/symbols.json` (генерируется `tools/analysis/build_symbol_map.py`).
    - Сниппет-индекс: `.cache/snippets.json` (генерируется `tools/analysis/build_snippet_index.py`).

## 3. Правила работы с Git и CI/CD
- **Инструменты в WSL:** Несмотря на возможность нативного запуска, инструменты `git`, `gh`, `git-lfs`, а также TUI-клиенты `lazygit` и `gitui` должны использоваться в WSL для консистентности путей и прав.
- **CI/CD:** Проверка статуса и просмотр логов GitHub Actions выполняется через `wsl gh run list/view`.
- **Коммиты:** Не делать коммиты без явного указания и никогда не логировать секреты.

## 4. Отладка и устранение неполадок
- **Интерактивность:** Если команды зависают в WSL из-за ожидания ввода или пейджера, необходимо установить переменные окружения: `GIT_PAGER=cat`, `PAGER=cat`, `DEBIAN_FRONTEND=noninteractive`.
- **Логирование:** ЗАПРЕЩЕНО использовать перенаправление `2>&1` в командах, так как это мешает автоматическому парсингу ошибок. Не перенаправлять вывод в файлы (`> run.log`) без необходимости.
- **Артефакты:** При отсутствии сети скрипты могут генерировать отладочные файлы `conn4_debug_*.json`.

## 5. Методология разработки и стандарты
- **Контекст:** Перед внесением правок файл всегда читается целиком. Ссылки на код в документации и диалогах оформляются через `file://` с указанием диапазонов строк.
- **Проверка:** После любых изменений кода ОБЯЗАТЕЛЬНО запускается соответствующий скрипт для верификации работоспособности.
- **Язык:** Общение, комментарии и документация ведутся на языке пользователя (русский).

## 6. Docker и OpenWrt SDK
- **Назначение:** Docker используется исключительно для OpenWrt SDK и изолированных тестов.
- **Гигиена:** Необходимо следить за размером образов и очищать кэш в рамках одной инструкции `RUN`. Регулярно выполнять `docker system prune -a`.
- **Диагностика:** Использовать `docker logs` для разбора проблем в контейнерах.

## 7. Тестирование Captive Portal
- **Сценарии:**
    - **NoJS:** `wsl python3 tools/test_conn4_portal_nojs.py`
    - **Selenium:** `wsl python3 tools/captive_portal_wsl_selenium.py` (требует настройки Chrome headless в WSL).
- **Логика старта и инициализации:**
    - **Выбор среды (CPM_ENV):** Переменная окружения `CPM_ENV` (`prod` или `dev`) определяет, к какому роутеру подключаться.
        - `prod` (по умолчанию) → `prod-openwrt` (192.168.x.x).
        - `dev` → `dev-openwrt` (192.168.1.1).
    - **Управление SOCKS-прокси:**
        - Скрипт принудительно завершает старые процессы SSH-туннеля на порту (10800).
        - Поднимает новый туннель к выбранному хосту.
        - Если туннель не поднялся (ошибка SSH/сети), скрипт немедленно завершается.
    - **Проверка авторизации (MSN/Microsoft):**
        - Скрипт открывает `www.msftconnecttest.com/redirect`.
        - Если происходит редирект на `msn.com` или `microsoft.com` — интернет уже есть, скрипт успешно завершает работу (`sys.exit(0)`).
        - Если редирект на `conn4.com` — начинается процесс авторизации.
    - **Параметры и ключи запуска:**
        - `--url <URL>`: Явное указание URL портала (перекрывает `SELENIUM_START_URL`).
        - `--out <FILE>`: Путь к файлу для сохранения токенов (по умолчанию `conn4_tokens.json`).
        - `--collect-tokens`: Режим «только сбор токенов» без попытки полной авторизации.
        - `--noform`: Пропустить взаимодействие с формами (автоматическое проставление галочек и нажатие кнопок).
        - `--write-compare`: Сохранять данные для сравнения (отладка).
    - **Переменные окружения (env):**
        - `SELENIUM_START_URL` / `PORTAL_START_URL`: Начальный URL.
        - `SELENIUM_COLLECT_TOKENS`: Включить режим сбора токенов (1/true).
        - `SELENIUM_NOFORM`: Отключить работу с формами (1/true).
        - `SELENIUM_RESTART_WWAN` / `RESTART_WWAN`: Принудительный сброс авторизации на роутере перед стартом.
        - `SELENIUM_REQUIRE_SOCKS`: Всегда использовать SOCKS, даже если интернет кажется доступным.
        - `CPM_BLOCK_EXTERNAL`: Блокировать загрузку внешних ресурсов (1 - включено по умолчанию).
- **Логика работы NoJS-скрипта:**
    - **Эмуляция браузера:** Использование `urllib` и `CookieJar` для работы с порталом без выполнения JavaScript.
    - **Работа с формами:** Автоматический парсинг HTML-форм и извлечение скрытых полей (tokens) для формирования POST-запросов.
    - **WBS API:** Прямое взаимодействие с API Wireless Billing System (`/wbs/api/v1/`) для завершения процесса авторизации.
    - **Фоллбек на Curl:** При обрывах соединения или специфических ошибках `urllib` скрипт переключается на выполнение запросов через `curl` с пробросом через SOCKS.
- **Логика работы Selenium-скрипта:**
    - **Инструментация (Hooking):** В каждую страницу и iframe инжектируется JS-код, который перехватывает вызовы `XMLHttpRequest`, `fetch`, `JSON.parse` и обращения к `localStorage/sessionStorage`. Это позволяет извлекать токены и API-сессии в реальном времени.
    - **Обнаружение портала:** Эмуляция входа через `msftconnecttest.com` с последующим отслеживанием редиректов на `conn4.com`.
    - **Блокировка внешних редиректов:** Скрипт принудительно блокирует уход на внешние сайты (например, `leonardo-hotels.com`), чтобы завершить сбор отладочных данных на самом портале.
    - **Динамическое ожидание:** Вместо фиксированных пауз используется мониторинг загрузки скриптов и появления ключевых элементов (кнопки "Get Free Wi-Fi").
    - **Автоматизация формы:** Поиск контейнеров авторизации, автоматическое проставление галочек (Accept Terms) и клик по кнопке входа (поиск по тексту и XPath).
    - **Сбор артефактов:** Полный дамп состояния: скриншоты, HTML, трассировка сессии в JSON и performance logs браузера.
- **Требования:** Для корректного тестирования необходим рабочий SOCKS-прокси, проверка эндпоинта `/_time` и настроенные маршруты к `conn4.com`.
