# Документ требований

## Введение

Данный документ описывает требования к автоматической отмене старых запущенных GitHub Actions workflow при мерже в main или запуске новой сборки. Цель - предотвратить избыточное использование ресурсов CI/CD и ускорить получение обратной связи за счет отмены устаревших сборок.

## Глоссарий

- **Workflow**: Автоматизированный процесс в GitHub Actions, определенный в YAML файле
- **Concurrency Group**: Группа workflow, которые не должны выполняться одновременно
- **Cancel-in-progress**: Механизм GitHub Actions для автоматической отмены предыдущих запусков workflow
- **Main Branch**: Основная ветка разработки (main)
- **Pull Request**: Запрос на слияние изменений в основную ветку
- **CI/CD Pipeline**: Конвейер непрерывной интеграции и доставки
- **Runner**: Виртуальная машина, выполняющая задачи GitHub Actions
- **Job**: Отдельная задача внутри workflow
- **Matrix Build**: Параллельная сборка для нескольких конфигураций

## Требования

### Требование 1

**User Story:** Как разработчик, я хочу чтобы при пуше в main автоматически отменялись все предыдущие запущенные workflow для этой же ветки, чтобы не тратить ресурсы на устаревшие сборки.

#### Критерии приемки

1. WHEN новый коммит пушится в main THEN система SHALL отменить все запущенные workflow для main
2. WHEN workflow отменяется THEN система SHALL освободить занятые runner ресурсы
3. WHEN отмена происходит THEN система SHALL сохранить логи отмененных workflow для отладки
4. WHEN новый workflow запускается THEN система SHALL использовать освободившиеся ресурсы
5. WHEN workflow уже завершился THEN система SHALL не пытаться его отменить

### Требование 2

**User Story:** Как разработчик, я хочу чтобы при создании нового коммита в pull request отменялись предыдущие сборки для этого же PR, чтобы получать обратную связь только по последним изменениям.

#### Критерии приемки

1. WHEN новый коммит добавляется в PR THEN система SHALL отменить предыдущие workflow для этого PR
2. WHEN workflow для PR отменяется THEN система SHALL сохранить workflow для других PR
3. WHEN несколько PR обновляются одновременно THEN система SHALL изолировать отмену для каждого PR
4. WHEN PR мержится THEN система SHALL завершить все workflow для этого PR
5. WHEN PR закрывается без мерджа THEN система SHALL отменить все активные workflow для этого PR

### Требование 3

**User Story:** Как DevOps инженер, я хочу настроить concurrency groups для всех workflow, чтобы обеспечить единообразную политику отмены.

#### Критерии приемки

1. WHEN workflow определяется THEN система SHALL включать секцию concurrency с уникальной группой
2. WHEN concurrency group определяется THEN группа SHALL использовать github.workflow и github.ref для уникальности
3. WHEN cancel-in-progress настраивается THEN значение SHALL быть true для PR и false для main
4. WHEN workflow для main запускается THEN система SHALL не отменять предыдущие workflow для main
5. WHEN workflow содержит matrix strategy THEN отмена SHALL применяться ко всем заданиям в matrix

### Требование 4

**User Story:** Как разработчик, я хочу чтобы workflow для релизных тегов никогда не отменялись, чтобы гарантировать создание всех артефактов релиза.

#### Критерии приемки

1. WHEN workflow запускается по тегу THEN система SHALL установить cancel-in-progress в false
2. WHEN несколько тегов создаются одновременно THEN система SHALL выполнить все workflow последовательно
3. WHEN релизный workflow выполняется THEN система SHALL не отменять его при новых коммитах в main
4. WHEN релизный workflow содержит matrix builds THEN система SHALL дождаться завершения всех заданий
5. WHEN релизный workflow завершается с ошибкой THEN система SHALL сохранить полные логи для анализа

### Требование 5

**User Story:** Как DevOps инженер, я хочу чтобы workflow для сборки Docker образов не отменялись при параллельных запусках, чтобы обеспечить создание всех образов.

#### Критерии приемки

1. WHEN workflow build-sdk-images запускается THEN система SHALL установить cancel-in-progress в false
2. WHEN несколько архитектур собираются параллельно THEN система SHALL завершить все сборки
3. WHEN сборка образа занимает длительное время THEN система SHALL не отменять её при новых коммитах
4. WHEN образ уже существует THEN система SHALL пропустить сборку без отмены workflow
5. WHEN сборка образа завершается THEN система SHALL загрузить образ в GHCR независимо от других workflow

### Требование 6

**User Story:** Как разработчик, я хочу чтобы CI workflow (lint, test) отменялись при новых коммитах в PR, чтобы быстрее получать результаты проверок.

#### Критерии приемки

1. WHEN CI workflow запускается для PR THEN система SHALL установить cancel-in-progress в true
2. WHEN новый коммит добавляется в PR THEN система SHALL отменить предыдущий CI workflow
3. WHEN CI workflow отменяется THEN система SHALL немедленно запустить новый workflow
4. WHEN CI workflow выполняется для main THEN система SHALL не отменять его
5. WHEN несколько linter заданий выполняются параллельно THEN отмена SHALL применяться ко всем заданиям

### Требование 7

**User Story:** Как разработчик, я хочу видеть статус отмененных workflow в GitHub UI, чтобы понимать почему сборка была остановлена.

#### Критерии приемки

1. WHEN workflow отменяется THEN система SHALL установить статус "Cancelled"
2. WHEN workflow отменяется THEN система SHALL показать причину отмены в логах
3. WHEN workflow отменяется автоматически THEN система SHALL указать "Superseded by newer run"
4. WHEN пользователь просматривает историю workflow THEN система SHALL показать все отмененные запуски
5. WHEN workflow отменяется THEN система SHALL сохранить частичные логи выполненных шагов

### Требование 8

**User Story:** Как DevOps инженер, я хочу чтобы release-please workflow не отменялся при параллельных запусках, чтобы гарантировать создание релиза.

#### Критерии приемки

1. WHEN release-please workflow запускается THEN система SHALL установить cancel-in-progress в false
2. WHEN несколько коммитов пушатся в main одновременно THEN система SHALL выполнить все release-please workflow последовательно
3. WHEN release-please создает PR THEN система SHALL завершить workflow независимо от новых коммитов
4. WHEN release-please создает тег THEN система SHALL гарантировать завершение всех шагов
5. WHEN release-please workflow выполняется THEN система SHALL не отменять его при новых пушах

### Требование 9

**User Story:** Как разработчик, я хочу чтобы workflow для ручного запуска (workflow_dispatch) не отменялись автоматически, чтобы иметь контроль над выполнением.

#### Критерии приемки

1. WHEN workflow запускается через workflow_dispatch THEN система SHALL использовать уникальную concurrency group
2. WHEN несколько ручных запусков происходят одновременно THEN система SHALL выполнить все запуски
3. WHEN ручной запуск выполняется THEN система SHALL не отменять его при автоматических триггерах
4. WHEN пользователь запускает workflow вручную THEN система SHALL показать опцию отмены в UI
5. WHEN ручной запуск отменяется пользователем THEN система SHALL немедленно остановить выполнение

### Требование 10

**User Story:** Как DevOps инженер, я хочу чтобы concurrency настройки были документированы в каждом workflow, чтобы понимать политику отмены.

#### Критерии приемки

1. WHEN workflow создается THEN файл SHALL содержать комментарии о concurrency политике
2. WHEN concurrency group определяется THEN комментарий SHALL объяснять логику группировки
3. WHEN cancel-in-progress устанавливается THEN комментарий SHALL объяснять причину выбора значения
4. WHEN workflow изменяется THEN документация SHALL обновляться соответственно
5. WHEN разработчик читает workflow THEN документация SHALL быть понятной без дополнительных источников

### Требование 11

**User Story:** Как разработчик, я хочу чтобы система автоматически очищала очередь ожидающих workflow, чтобы не накапливались устаревшие задачи.

#### Критерии приемки

1. WHEN workflow находится в очереди ожидания THEN система SHALL отменить его при появлении нового workflow
2. WHEN несколько workflow ожидают в очереди THEN система SHALL отменить все кроме последнего
3. WHEN workflow начал выполнение THEN система SHALL дождаться завершения текущего шага перед отменой
4. WHEN очередь очищается THEN система SHALL сохранить информацию об отмененных workflow
5. WHEN ресурсы освобождаются THEN система SHALL немедленно запустить следующий workflow из очереди

### Требование 12

**User Story:** Как DevOps инженер, я хочу мониторить количество отмененных workflow, чтобы оптимизировать CI/CD процесс.

#### Критерии приемки

1. WHEN workflow отменяется THEN система SHALL записать метрику в GitHub Actions
2. WHEN метрики собираются THEN система SHALL включать причину отмены
3. WHEN метрики анализируются THEN система SHALL показать тренд отмен по времени
4. WHEN слишком много отмен происходит THEN система SHALL предупредить в логах
5. WHEN workflow завершается успешно THEN система SHALL записать время выполнения для сравнения
