# Requirements Document: Restore Missing Releases

## Introduction

Проект мигрировал с семантического версионирования (v0.1.x, v1.0.x) на датированное автоматическое версионирование (vYYYY.M.D.N) в январе 2025 года. В процессе миграции и последующей разработки были удалены критически важные исторические теги и релизы:

**Удалённые семантические версии (приоритет 1 - критично):**
- v0.1.0 - первый публичный релиз
- v0.1.1 - улучшения packaging и CI
- v0.1.2 - исправления совместимости SDK
- v1.0.1 - крупное обновление документации
- v1.0.3 - синхронизация версионирования

**Отсутствующие датированные релизы (приоритет 2):**
- v2025.11.21.34
- v2025.11.22.1, v2025.11.22.99, v2025.11.22.100
- v2025.11.27.10, v2025.11.27.11, v2025.11.27.12

Необходимо восстановить все эти релизы для обеспечения полной истории версий проекта, особенно критично восстановить семантические версии, так как они документируют начальную историю проекта.

## Glossary

- **Tag**: Git тег, указывающий на конкретный коммит в истории
- **Release**: GitHub релиз, связанный с тегом, содержащий changelog и артефакты
- **System**: Система управления релизами проекта
- **Missing Release**: Тег был удалён из Git и соответствующий GitHub релиз отсутствует
- **Semantic Version**: Версия в формате vMAJOR.MINOR.PATCH (например, v1.0.3)
- **Date-based Version**: Версия в формате vYYYY.M.D.N (например, v2025.11.27.13)
- **Historical Release**: Релиз с семантическим версионированием, созданный до миграции на датированное версионирование

## Requirements

### Requirement 1

**User Story:** Как разработчик, я хочу восстановить исторические семантические релизы, чтобы сохранить начальную историю проекта.

#### Acceptance Criteria

1. WHEN система восстанавливает семантический релиз THEN система SHALL воссоздать тег на основе информации из CHANGELOG.md
2. WHEN создается исторический релиз THEN система SHALL использовать changelog из CHANGELOG.md для описания релиза
3. WHEN создается семантический релиз THEN система SHALL пометить его как "Historical Release - Restored from CHANGELOG"
4. WHEN все семантические релизы восстановлены THEN система SHALL проверить наличие релизов для v0.1.0, v0.1.1, v0.1.2, v1.0.1, v1.0.3

### Requirement 2

**User Story:** Как разработчик, я хочу восстановить отсутствующие датированные релизы, чтобы история версий после миграции была полной.

#### Acceptance Criteria

1. WHEN система обнаруживает датированный тег без релиза THEN система SHALL создать GitHub релиз для этого тега
2. WHEN создается релиз для датированного тега THEN система SHALL генерировать changelog на основе коммитов между предыдущим и текущим тегом
3. WHEN создается датированный релиз THEN система SHALL использовать формат заголовка "vYYYY.M.D.N - YYYY-MM-DD"
4. WHEN все датированные релизы созданы THEN система SHALL проверить, что каждый датированный тег имеет соответствующий релиз

### Requirement 3

**User Story:** Как пользователь проекта, я хочу видеть полную историю изменений, чтобы понимать эволюцию проекта от первого релиза до текущего.

#### Acceptance Criteria

1. WHEN пользователь просматривает список релизов THEN система SHALL отображать все релизы в хронологическом порядке, включая исторические
2. WHEN пользователь открывает исторический релиз THEN система SHALL показывать changelog из CHANGELOG.md
3. WHEN пользователь открывает датированный релиз THEN система SHALL показывать changelog на основе коммитов
4. WHEN релиз восстановлен автоматически THEN система SHALL пометить его как "Restored" в описании

### Requirement 4

**User Story:** Как администратор проекта, я хочу иметь скрипт для автоматического восстановления релизов, чтобы избежать ручной работы.

#### Acceptance Criteria

1. WHEN запускается скрипт восстановления THEN система SHALL сначала восстановить семантические релизы, затем датированные
2. WHEN восстанавливаются семантические релизы THEN система SHALL использовать CHANGELOG.md как источник информации
3. WHEN восстанавливаются датированные релизы THEN система SHALL использовать git log для генерации changelog
4. WHEN скрипт завершается THEN система SHALL вывести отчет о восстановленных релизах с разделением по типам
5. WHEN происходит ошибка при создании релиза THEN система SHALL продолжить обработку остальных релизов и вывести список ошибок

### Requirement 5

**User Story:** Как разработчик, я хочу проверить целостность релизов, чтобы убедиться, что вся история версий восстановлена.

#### Acceptance Criteria

1. WHEN запускается проверка целостности THEN система SHALL проверить наличие всех семантических релизов из CHANGELOG.md
2. WHEN запускается проверка целостности THEN система SHALL проверить наличие релизов для всех датированных тегов
3. WHEN обнаружены отсутствующие релизы THEN система SHALL вывести список отсутствующих релизов с указанием типа
4. WHEN все релизы присутствуют THEN система SHALL вывести сообщение об успешной проверке с количеством релизов каждого типа
