# Требования к оптимизации сборки пакетов OpenWrt

## Введение

Данный документ описывает требования к оптимизации процесса сборки пакетов OpenWrt для проекта openwrt-captive-monitor. Цель - ускорить сборку при каждом мерже в main через использование кешированных Docker-образов, хранящихся в GitHub Container Registry, и оптимизацию workflow GitHub Actions.

## Глоссарий

- **SDK** (Software Development Kit): Набор инструментов OpenWrt для кросс-компиляции пакетов
- **GHCR** (GitHub Container Registry): Реестр контейнеров GitHub для хранения Docker-образов
- **Workflow**: Автоматизированный процесс в GitHub Actions
- **Artifact**: Результат сборки (файл .ipk пакета)
- **Main Branch**: Основная ветка разработки (main)
- **Pull Request**: Запрос на слияние изменений в основную ветку
- **Docker Image**: Контейнерный образ с предустановленным окружением сборки
- **Build System**: Система сборки, включающая все компоненты для компиляции пакетов

## Требования

### Требование 1

**User Story:** Как разработчик, я хочу чтобы сборка пакета при мерже в main выполнялась быстро, чтобы получать обратную связь о качестве кода в течение нескольких минут.

#### Критерии приемки

1. WHEN изменения мержатся в main THEN система SHALL запустить автоматическую сборку пакета
2. WHEN сборка использует кешированный Docker-образ THEN время сборки SHALL быть менее 5 минут
3. WHEN Docker-образ отсутствует в кеше THEN система SHALL собрать и закешировать новый образ
4. WHEN сборка завершается успешно THEN система SHALL создать артефакт с .ipk файлом
5. WHEN сборка завершается с ошибкой THEN система SHALL предоставить детальный лог ошибки

### Требование 2

**User Story:** Как DevOps инженер, я хочу хранить предсобранные Docker-образы с OpenWrt SDK в GHCR, чтобы избежать повторной загрузки и распаковки SDK при каждой сборке.

#### Критерии приемки

1. WHEN система создает Docker-образ THEN образ SHALL содержать предустановленный OpenWrt SDK
2. WHEN Docker-образ создан THEN система SHALL загрузить образ в GHCR с соответствующими тегами
3. WHEN workflow запускается THEN система SHALL использовать Docker-образ из GHCR
4. WHEN версия OpenWrt обновляется THEN система SHALL создать новый Docker-образ с обновленной версией
5. WHEN Docker-образ используется THEN система SHALL пропустить этапы загрузки и распаковки SDK

### Требование 3

**User Story:** Как разработчик, я хочу использовать workflow с branch → pull request → merge в main, чтобы обеспечить проверку кода перед интеграцией.

#### Критерии приемки

1. WHEN разработчик создает feature branch THEN система SHALL позволить создание ветки без ограничений
2. WHEN разработчик создает pull request THEN система SHALL запустить CI проверки (lint, test, build)
3. WHEN все CI проверки проходят успешно THEN система SHALL разрешить мерж в main
4. WHEN pull request мержится в main THEN система SHALL запустить полную сборку пакета
5. WHEN мерж в main завершается THEN система SHALL создать и сохранить артефакты сборки

### Требование 4

**User Story:** Как DevOps инженер, я хочу оптимизировать использование кеша GitHub Actions, чтобы минимизировать время загрузки зависимостей.

#### Критерии приемки

1. WHEN workflow использует зависимости THEN система SHALL кешировать зависимости с уникальным ключом
2. WHEN кеш существует THEN система SHALL восстановить зависимости из кеша
3. WHEN кеш устарел THEN система SHALL обновить кеш с новыми зависимостями
4. WHEN несколько workflow используют одинаковые зависимости THEN система SHALL переиспользовать общий кеш
5. WHEN кеш поврежден THEN система SHALL пересоздать кеш с нуля

### Требование 5

**User Story:** Как разработчик, я хочу чтобы Docker-образы автоматически обновлялись при изменении Dockerfile, чтобы всегда использовать актуальное окружение сборки.

#### Критерии приемки

1. WHEN Dockerfile изменяется THEN система SHALL обнаружить изменения
2. WHEN изменения в Dockerfile обнаружены THEN система SHALL пересобрать Docker-образ
3. WHEN Docker-образ пересобран THEN система SHALL загрузить новый образ в GHCR
4. WHEN новый образ загружен THEN система SHALL использовать новый образ в последующих сборках
5. WHEN пересборка образа происходит THEN система SHALL сохранить предыдущую версию образа с тегом

### Требование 6

**User Story:** Как разработчик, я хочу чтобы сборка поддерживала множественные архитектуры OpenWrt, чтобы создавать пакеты для различных устройств.

#### Критерии приемки

1. WHEN сборка запускается для релиза THEN система SHALL собрать пакеты для всех поддерживаемых архитектур
2. WHEN сборка для PR запускается THEN система SHALL собрать пакет только для одной тестовой архитектуры
3. WHEN сборка для архитектуры завершается THEN система SHALL создать соответствующий .ipk файл
4. WHEN все архитектуры собраны THEN система SHALL агрегировать все артефакты
5. WHEN архитектура не поддерживается THEN система SHALL пропустить сборку для этой архитектуры

### Требование 7

**User Story:** Как DevOps инженер, я хочу использовать matrix strategy в GitHub Actions, чтобы параллельно собирать пакеты для разных архитектур.

#### Критерии приемки

1. WHEN workflow использует matrix strategy THEN система SHALL запустить параллельные задания для каждой архитектуры
2. WHEN одно задание в matrix завершается с ошибкой THEN система SHALL продолжить выполнение остальных заданий
3. WHEN все задания в matrix завершаются THEN система SHALL агрегировать результаты
4. WHEN matrix содержит более 5 архитектур THEN система SHALL ограничить параллельное выполнение
5. WHEN задание в matrix использует ресурсы THEN система SHALL изолировать ресурсы между заданиями

### Требование 8

**User Story:** Как разработчик, я хочу чтобы коммиты в GitHub были на английском языке, чтобы обеспечить международную совместимость проекта.

#### Критерии приемки

1. WHEN разработчик создает коммит THEN сообщение коммита SHALL быть на английском языке
2. WHEN коммит содержит технические термины THEN термины SHALL использовать стандартную английскую терминологию
3. WHEN коммит описывает изменения THEN описание SHALL следовать conventional commits формату
4. WHEN коммит создается автоматически THEN система SHALL генерировать сообщение на английском языке
5. WHEN коммит содержит ссылки на issues THEN ссылки SHALL быть корректно отформатированы

### Требование 9

**User Story:** Как разработчик, я хочу использовать WSL (Windows Subsystem for Linux) версии 1 для работы с Git, чтобы обеспечить совместимость с Windows окружением.

#### Критерии приемки

1. WHEN разработчик использует Git команды THEN команды SHALL выполняться через WSL1
2. WHEN WSL1 выполняет Git операции THEN операции SHALL корректно обрабатывать пути Windows
3. WHEN создается новая ветка THEN система SHALL использовать Git CLI через WSL1
4. WHEN создается pull request THEN система SHALL использовать GitHub CLI через WSL1
5. WHEN происходит мерж THEN система SHALL использовать Git CLI через WSL1

### Требование 10

**User Story:** Как DevOps инженер, я хочу чтобы Docker-образы были оптимизированы по размеру, чтобы минимизировать время загрузки и использование хранилища.

#### Критерии приемки

1. WHEN Docker-образ создается THEN система SHALL использовать multi-stage build для минимизации размера
2. WHEN образ содержит зависимости THEN система SHALL удалить временные файлы и кеши
3. WHEN образ загружается в GHCR THEN размер образа SHALL быть менее 2GB
4. WHEN образ используется THEN система SHALL использовать layer caching для ускорения загрузки
5. WHEN образ содержит SDK THEN система SHALL включить только необходимые компоненты SDK

### Требование 11

**User Story:** Как разработчик, я хочу чтобы документация и планы были на русском языке, чтобы облегчить понимание для русскоязычной команды.

#### Критерии приемки

1. WHEN создается документация спецификации THEN документация SHALL быть на русском языке
2. WHEN создается план задач THEN план SHALL быть на русском языке
3. WHEN создается design документ THEN документ SHALL быть на русском языке
4. WHEN документация содержит технические термины THEN термины SHALL сопровождаться английскими эквивалентами
5. WHEN документация ссылается на код THEN примеры кода SHALL содержать комментарии на русском языке

### Требование 12

**User Story:** Как DevOps инженер, я хочу чтобы система автоматически очищала старые Docker-образы, чтобы не переполнять хранилище GHCR.

#### Критерии приемки

1. WHEN Docker-образ старше 90 дней THEN система SHALL пометить образ для удаления
2. WHEN образ не используется в течение 30 дней THEN система SHALL удалить неиспользуемый образ
3. WHEN существует более 10 версий образа THEN система SHALL сохранить только последние 10 версий
4. WHEN образ помечен как latest THEN система SHALL не удалять этот образ
5. WHEN образ используется в активном workflow THEN система SHALL не удалять этот образ
