# Проектирование оптимизации сборки пакетов OpenWrt

## Обзор

Данный документ описывает архитектуру и дизайн системы оптимизации сборки пакетов OpenWrt для проекта openwrt-captive-monitor. Решение основано на использовании предсобранных Docker-образов с OpenWrt SDK, хранящихся в GitHub Container Registry (GHCR), и оптимизированных GitHub Actions workflows.

### Текущее состояние

Существующая система сборки:
- Использует `openwrt/gh-action-sdk@v9` для сборки пакетов
- Кеширует SDK через GitHub Actions cache (~500MB-1GB)
- Время сборки: 3-7 минут при наличии кеша, 10-15 минут без кеша
- Поддерживает 8 архитектур для релизных сборок
- Использует matrix strategy для параллельной сборки

### Целевое состояние

Оптимизированная система сборки:
- Docker-образы с предустановленным SDK в GHCR
- Время сборки: < 3 минут при использовании образа
- Автоматическое обновление образов при изменении Dockerfile
- Улучшенное кеширование зависимостей
- Оптимизированный workflow для PR и main веток

### Поток данных

1. **Обновление Docker-образа**:
   - Изменение Dockerfile → Trigger workflow → Build image → Push to GHCR

2. **Сборка при PR**:
   - Create PR → Lint + Test → Build (1 arch) → Upload artifacts

3. **Сборка при merge в main**:
   - Merge to main → Pull image from GHCR → Build (1 arch) → Upload artifacts

4. **Релизная сборка**:
   - Tag push → Pull image from GHCR → Build (8 archs, parallel) → Create release

## Компоненты и интерфейсы

### 1. Docker-образ SDK

**Назначение**: Предоставить готовое окружение сборки с предустановленным OpenWrt SDK.

**Структура Dockerfile**:
```dockerfile
FROM ubuntu:24.04

# Установка зависимостей
RUN apt-get update && apt-get install -y \
    build-essential \
    curl \
    git \
    python3 \
    && rm -rf /var/lib/apt/lists/*

# Загрузка и распаковка SDK
ARG OPENWRT_VERSION=23.05.5
ARG SDK_TARGET=x86-64
ARG SDK_URL=https://downloads.openwrt.org/releases/${OPENWRT_VERSION}/targets/${SDK_TARGET}/...

RUN curl -fsSL ${SDK_URL} -o /tmp/sdk.tar.xz && \
    mkdir -p /opt/openwrt-sdk && \
    tar -C /opt/openwrt-sdk --strip-components=1 -xf /tmp/sdk.tar.xz && \
    rm /tmp/sdk.tar.xz

WORKDIR /opt/openwrt-sdk
```

**Теги образов**:
- `ghcr.io/nagual2/openwrt-sdk:23.05.5-x86-64-latest`
- `ghcr.io/nagual2/openwrt-sdk:23.05.5-x86-64-{sha}`
- `ghcr.io/nagual2/openwrt-sdk:23.05.5-ath79-generic-latest`

### 2. Workflow для сборки Docker-образов

**Файл**: `.github/workflows/build-sdk-images.yml`

**Триггеры**:
- Push в main с изменениями в `docker/sdk/Dockerfile`
- Ручной запуск (workflow_dispatch)
- Расписание (еженедельно для обновления базового образа)

**Задачи**:
1. Определить список архитектур для сборки
2. Собрать образы параллельно (matrix strategy)
3. Загрузить образы в GHCR с тегами
4. Обновить манифест образов

### 3. Оптимизированный CI Workflow

**Файл**: `.github/workflows/ci-optimized.yml`

**Изменения относительно текущего**:
- Использование Docker-образа вместо кеширования SDK
- Упрощенная подготовка окружения
- Улучшенное кеширование зависимостей feeds

**Структура**:
```yaml
jobs:
  lint: # без изменений
  test: # без изменений
  
  build-pr-package:
    runs-on: ubuntu-24.04
    container:
      image: ghcr.io/nagual2/openwrt-sdk:23.05.5-x86-64-latest
    steps:
      - checkout
      - prepare package structure
      - build package (SDK уже готов!)
      - validate and upload
```

### 4. Workflow для очистки старых образов

**Файл**: `.github/workflows/cleanup-images.yml`

**Триггеры**:
- Расписание (ежедневно)
- Ручной запуск

**Логика очистки**:
- Сохранить образы с тегом `latest`
- Сохранить последние 10 версий каждой архитектуры
- Удалить образы старше 90 дней
- Удалить неиспользуемые образы (без pulls за 30 дней)

### 5. Скрипты для работы с Git через WSL1

**Файл**: `scripts/git-wsl.sh`

**Функции**:
- `create_branch()` - создание ветки через WSL1
- `create_pr()` - создание PR через GitHub CLI в WSL1
- `merge_pr()` - мерж PR через WSL1
- `commit()` - создание коммита с английским сообщением

**Интерфейс**:
```bash
# Создание feature ветки
./scripts/git-wsl.sh create-branch "feature/optimize-build"

# Создание PR
./scripts/git-wsl.sh create-pr "Optimize build process" "Description..."

# Мерж PR
./scripts/git-wsl.sh merge-pr 123
```

## Correctness Properties

*Свойство (property) - это характеристика или поведение, которое должно выполняться во всех допустимых выполнениях системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинно-проверяемыми гарантиями корректности.*

### Property 1: Успешная сборка создает артефакты

*Для любой* успешно завершенной сборки пакета, система должна создать соответствующий .ipk файл в директории артефактов.

**Валидирует: Требования 1.4**

### Property 2: Docker-образ содержит SDK

*Для любого* созданного Docker-образа SDK, образ должен содержать предустановленный и распакованный OpenWrt SDK в директории `/opt/openwrt-sdk`.

**Валидирует: Требования 2.1**

### Property 3: Образы загружаются с правильными тегами

*Для любого* Docker-образа, загруженного в GHCR, образ должен иметь теги в формате `{version}-{arch}-latest` и `{version}-{arch}-{sha}`.

**Валидирует: Требования 2.2**

### Property 4: Мерж в main создает артефакты

*Для любого* успешного мерджа в ветку main, система должна создать и сохранить артефакты сборки (.ipk файлы и SHA256SUMS).

**Валидирует: Требования 3.5**

### Property 5: Кеш использует уникальные ключи

*Для любого* workflow, использующего кеширование зависимостей, ключ кеша должен включать уникальные идентификаторы (OS, тип зависимостей, хеш файлов конфигурации).

**Валидирует: Требования 4.1**

### Property 6: Переиспользование кеша между workflow

*Для любых* двух workflow, использующих одинаковые зависимости, система должна использовать один и тот же кеш (одинаковый ключ кеша).

**Валидирует: Требования 4.4**

### Property 7: Пересборка образа при изменении Dockerfile

*Для любого* изменения в Dockerfile, система должна загрузить новый образ в GHCR с обновленным тегом.

**Валидирует: Требования 5.3**

### Property 8: Сохранение предыдущих версий образов

*Для любой* пересборки Docker-образа, предыдущая версия образа должна остаться в GHCR с соответствующим тегом (не latest).

**Валидирует: Требования 5.5**

### Property 9: Релизная сборка для всех архитектур

*Для любой* релизной сборки (tag push), система должна создать .ipk файлы для всех архитектур, определенных в release_matrix.

**Валидирует: Требования 6.1**

### Property 10: Сборка создает .ipk для архитектуры

*Для любой* архитектуры в matrix, успешная сборка должна создать .ipk файл с именем, содержащим идентификатор архитектуры.

**Валидирует: Требования 6.3**

### Property 11: Автоматические коммиты на английском

*Для любого* автоматически созданного коммита (например, version bump), сообщение коммита должно быть на английском языке и следовать conventional commits формату.

**Валидирует: Требования 8.4**

### Property 12: Форматирование ссылок на issues

*Для любого* коммита, содержащего ссылку на issue, ссылка должна быть в формате `#<номер>` или полном URL формате GitHub.

**Валидирует: Требования 8.5**

### Property 13: WSL1 корректно обрабатывает пути

*Для любой* Git операции, выполняемой через WSL1, пути Windows (например, `C:\Users\...`) должны корректно преобразовываться в пути Linux (например, `/mnt/c/Users/...`).

**Валидирует: Требования 9.2**

### Property 14: Образ удаляет временные файлы

*Для любого* Docker-образа, содержащего зависимости, образ не должен содержать временные файлы сборки (например, `/tmp/*`, `/var/cache/apt/*`).

**Валидирует: Требования 10.2**

### Property 15: Размер образа менее 2GB

*Для любого* Docker-образа, загруженного в GHCR, размер образа должен быть менее 2GB.

**Валидирует: Требования 10.3**

### Property 16: Образ содержит только необходимые компоненты SDK

*Для любого* Docker-образа с SDK, образ должен содержать только необходимые компоненты SDK (исключая документацию, примеры, исходники ядра).

**Валидирует: Требования 10.5**

### Property 17: Удаление образов старше 90 дней

*Для любого* Docker-образа в GHCR, если образ старше 90 дней и не помечен как `latest`, он должен быть помечен для удаления.

**Валидирует: Требования 12.1**

### Property 18: Удаление неиспользуемых образов

*Для любого* Docker-образа в GHCR, если образ не использовался (не было pulls) в течение 30 дней, он должен быть удален.

**Валидирует: Требования 12.2**

### Property 19: Сохранение последних 10 версий

*Для любой* архитектуры, в GHCR должно храниться не более 10 последних версий образов (исключая `latest`).

**Валидирует: Требования 12.3**

### Property 20: Защита образов с тегом latest

*Для любого* Docker-образа с тегом `latest`, образ не должен удаляться автоматической очисткой.

**Валидирует: Требования 12.4**

### Property 21: Защита активно используемых образов

*Для любого* Docker-образа, используемого в активном workflow (запущенном в последние 24 часа), образ не должен удаляться.

**Валидирует: Требования 12.5**

## Error Handling

### Обработка ошибок сборки

**Сценарий**: Сборка пакета завершается с ошибкой

**Обработка**:
1. Workflow должен завершиться с кодом ошибки
2. Детальный лог сборки должен быть доступен в GitHub Actions
3. Для matrix builds с `fail-fast: false`, остальные задания продолжают выполнение
4. Артефакты не создаются для неудачных сборок

### Обработка отсутствия Docker-образа

**Сценарий**: Docker-образ отсутствует в GHCR

**Обработка**:
1. Workflow должен автоматически запустить сборку образа
2. После успешной сборки образа, основной workflow должен продолжиться
3. Если сборка образа не удалась, workflow завершается с ошибкой

### Обработка поврежденного кеша

**Сценарий**: Кеш GitHub Actions поврежден или несовместим

**Обработка**:
1. Workflow должен обнаружить ошибку при восстановлении кеша
2. Кеш должен быть проигнорирован
3. Зависимости должны быть загружены заново
4. Новый кеш должен быть создан после успешной загрузки

### Обработка ошибок WSL1

**Сценарий**: WSL1 недоступен или команда завершается с ошибкой

**Обработка**:
1. Скрипт должен проверить доступность WSL1 перед выполнением команд
2. При недоступности WSL1, скрипт должен вывести понятное сообщение об ошибке
3. Скрипт должен завершиться с ненулевым кодом возврата
4. Пользователь должен получить инструкции по устранению проблемы

### Обработка ошибок GHCR

**Сценарий**: Ошибка при загрузке или скачивании образа из GHCR

**Обработка**:
1. Workflow должен повторить попытку до 3 раз с экспоненциальной задержкой
2. При исчерпании попыток, workflow завершается с ошибкой
3. Детальное сообщение об ошибке должно быть записано в лог
4. Уведомление должно быть отправлено в GitHub Actions summary

### Обработка ошибок очистки образов

**Сценарий**: Ошибка при удалении старых образов из GHCR

**Обработка**:
1. Workflow должен продолжить обработку остальных образов
2. Ошибки должны быть записаны в лог
3. Workflow должен завершиться с предупреждением (не с ошибкой)
4. Список необработанных образов должен быть выведен в summary

## Testing Strategy

### Подход к тестированию

Система оптимизации сборки будет тестироваться на двух уровнях:

1. **Unit тесты** - для проверки отдельных скриптов и компонентов
2. **Integration тесты** - для проверки взаимодействия компонентов и workflow

### Unit тестирование

**Тестируемые компоненты**:

1. **Скрипт git-wsl.sh**
   - Проверка корректного преобразования путей Windows в Linux
   - Проверка создания коммитов с английскими сообщениями
   - Проверка форматирования ссылок на issues

2. **Скрипты валидации**
   - Проверка валидации размера Docker-образа
   - Проверка валидации содержимого образа
   - Проверка валидации артефактов сборки

3. **Скрипты очистки**
   - Проверка логики определения образов для удаления
   - Проверка защиты образов с тегом latest
   - Проверка защиты активно используемых образов

**Инструменты**:
- `shellcheck` для статического анализа shell скриптов
- `bats` (Bash Automated Testing System) для unit тестов
- `shunit2` как альтернатива для простых тестов

### Integration тестирование

**Тестовые сценарии**:

1. **Полный цикл сборки при PR**
   - Создание PR
   - Запуск CI проверок
   - Проверка создания артефактов для одной архитектуры
   - Проверка времени сборки < 5 минут

2. **Полный цикл сборки при мерже в main**
   - Мерж PR в main
   - Запуск сборки
   - Проверка создания артефактов
   - Проверка загрузки артефактов

3. **Полный цикл релизной сборки**
   - Создание тега
   - Запуск релизной сборки
   - Проверка сборки для всех 8 архитектур
   - Проверка создания GitHub Release
   - Проверка загрузки всех артефактов

4. **Цикл обновления Docker-образа**
   - Изменение Dockerfile
   - Запуск workflow сборки образа
   - Проверка загрузки нового образа в GHCR
   - Проверка сохранения старой версии
   - Проверка использования нового образа в следующей сборке

5. **Цикл очистки старых образов**
   - Запуск workflow очистки
   - Проверка удаления образов старше 90 дней
   - Проверка сохранения последних 10 версий
   - Проверка защиты образов с тегом latest

**Инструменты**:
- GitHub Actions для запуска тестовых workflow
- `act` для локального тестирования GitHub Actions
- Docker для тестирования образов
- `gh` CLI для взаимодействия с GitHub API

### Тестирование производительности

**Метрики**:

1. **Время сборки**
   - Целевое значение: < 3 минут с Docker-образом
   - Измерение: время от начала до конца job в GitHub Actions
   - Сравнение с текущим временем сборки (3-7 минут)

2. **Размер Docker-образа**
   - Целевое значение: < 2GB
   - Измерение: размер образа в GHCR
   - Мониторинг роста размера при обновлениях

3. **Использование кеша**
   - Метрика: процент успешных восстановлений кеша
   - Целевое значение: > 90%
   - Измерение: логи GitHub Actions

4. **Время загрузки образа**
   - Метрика: время загрузки образа из GHCR
   - Целевое значение: < 1 минуты
   - Измерение: логи GitHub Actions

### Continuous Testing

**Автоматическое тестирование**:

1. **При каждом PR**
   - Запуск unit тестов
   - Запуск линтеров
   - Тестовая сборка для одной архитектуры

2. **При мерже в main**
   - Полный набор unit тестов
   - Integration тесты
   - Сборка для одной архитектуры

3. **При создании тега**
   - Полный набор тестов
   - Релизная сборка для всех архитектур
   - Валидация всех артефактов

4. **По расписанию (еженедельно)**
   - Полный набор integration тестов
   - Тестирование производительности
   - Проверка работы очистки образов

### Мониторинг и алертинг

**Метрики для мониторинга**:

1. Время сборки (среднее, медиана, 95-й перцентиль)
2. Процент успешных сборок
3. Размер Docker-образов
4. Использование хранилища GHCR
5. Процент успешных восстановлений кеша

**Алерты**:

1. Время сборки превышает 5 минут
2. Процент успешных сборок падает ниже 95%
3. Размер образа превышает 2GB
4. Использование хранилища GHCR превышает 80%
5. Процент успешных восстановлений кеша падает ниже 80%
