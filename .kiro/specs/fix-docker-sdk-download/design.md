# Design Document

## Overview

Этот документ описывает дизайн решения для исправления проблемы загрузки OpenWrt SDK в Docker образе. Проблема заключается в неправильном формировании имени файла SDK и URL для некоторых архитектур, что приводит к ошибкам 404 при попытке скачать SDK.

Основная проблема: скрипт `download-sdk.sh` использует упрощенную логику определения суффикса MUSL (`_musl` или `_musl_eabi`), которая не покрывает все архитектуры OpenWrt. Некоторые архитектуры используют другие суффиксы или вообще не используют MUSL.

## Architecture

Решение состоит из следующих компонентов:

1. **Улучшенный скрипт загрузки SDK** (`download-sdk.sh`)
   - Точное определение суффикса для каждой архитектуры
   - Детальная диагностика ошибок
   - Устойчивость к сетевым проблемам

2. **Dockerfile** (минимальные изменения)
   - Использует улучшенный скрипт загрузки
   - Сохраняет multi-stage build структуру

3. **Workflow для сборки образов** (без изменений)
   - Уже существует и работает корректно
   - Использует обновленный Dockerfile

## Components and Interfaces

### 1. Скрипт загрузки SDK (`download-sdk.sh`)

**Входные параметры (переменные окружения):**
- `OPENWRT_VERSION` - версия OpenWrt (например, "23.05.5")
- `SDK_TARGET` - целевая архитектура (например, "x86", "ath79")
- `SDK_SUBTARGET` - подархитектура (например, "64", "generic")

**Выходные данные:**
- Скачанный и распакованный SDK в `/opt/openwrt-sdk`
- Верифицированная контрольная сумма

**Функции:**

```bash

}
```

## Data Models

### Маппинг архитектур на суффиксы MUSL

```
x86/64          -> _musl
ath79/generic   -> _musl
ramips/mt76x8   -> _musl
mediatek/filogic -> _musl
ipq40xx/generic -> _musl_eabi
ipq806x/generic -> _musl_eabi
bcm27xx/bcm2711 -> _musl
rockchip/armv8  -> _musl
```

### Формат имени файла SDK

```
openwrt-sdk-{VERSION}-{TARGET}-{SUBTARGET}_gcc-{GCC_VERSION}{MUSL_SUFFIX}.Linux-x86_64.tar.xz
```

Пример:
```
openwrt-sdk-23.05.5-x86-64_gcc-12.3.0_musl.Linux-x86_64.tar.xz
```

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system-essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

### Property 1: Правильное формирование URL для всех архитектур

*For any* поддерживаемой комбинации target/subtarget, скрипт должен сформировать корректный URL, который существует на сервере OpenWrt и возвращает HTTP 200.

**Validates: Requirements 1.1, 1.2**

### Property 2: Успешная верификация контрольной суммы

*For any* успешно скачанного SDK файла, верификация контрольной суммы должна пройти успешно, подтверждая целостность файла.

**Validates: Requirements 1.3**

### Property 3: Retry при сетевых ошибках

*For any* временной сетевой ошибки (5xx, timeout, connection reset), скрипт должен повторить попытку с экспоненциальной задержкой до 15 раз.

**Validates: Requirements 3.1, 3.3**

### Property 4: Продолжение прерванной загрузки

*For any* прерванной загрузки, скрипт должен использовать curl с опцией `-C -` для продолжения загрузки с места обрыва.

**Validates: Requirements 3.2**

### Property 5: Детальная диагностика ошибок

*For any* ошибки загрузки или верификации, скрипт должен вывести:
- Полный URL файла
- Код ошибки HTTP/curl
- Список доступных файлов (при 404)
- Ожидаемую и полученную контрольные суммы (при ошибке верификации)

**Validates: Requirements 2.1, 2.2, 2.3, 2.4**

### Property 6: Распаковка SDK в правильную директорию

*For any* успешно скачанного и верифицированного SDK, файл должен быть распакован в `/opt/openwrt-sdk` с удалением корневой директории из архива.

**Validates: Requirements 1.4**

## Error Handling

### Типы ошибок

1. **Ошибки формирования URL**
   - Неизвестная архитектура
   - Отсутствие обязательных переменных окружения
   - Действие: Вывести ошибку и завершить с кодом 1

2. **Сетевые ошибки**
   - Timeout
   - Connection refused
   - DNS resolution failed
   - Действие: Retry с экспоненциальной задержкой (1s, 2s, 4s, 8s, ...)

3. **HTTP ошибки**
   - 404 Not Found: Вывести список доступных файлов, завершить с кодом 1
   - 5xx Server Error: Retry до 15 раз
   - 4xx Client Error (кроме 404): Вывести ошибку, завершить с кодом 1

4. **Ошибки верификации**
   - Несовпадение контрольной суммы
   - Действие: Вывести ожидаемую и полученную суммы, удалить файл, завершить с кодом 1

5. **Ошибки распаковки**
   - Поврежденный архив
   - Недостаточно места на диске
   - Действие: Вывести ошибку tar, завершить с кодом 1

### Стратегия обработки ошибок

```bash
set -e  # Завершить при любой ошибке
set -u  # Ошибка при использовании неопределенных переменных
set -o pipefail  # Ошибка в любой части pipeline
```

Для операций с retry:
```bash
for attempt in $(seq 1 15); do
    if curl ...; then
        break
    fi
    if [ $attempt -lt 15 ]; then
        delay=$((2 ** attempt))
        echo "Retry $attempt/15 after ${delay}s..."
        sleep $delay
    else
        echo "All retry attempts exhausted"
        exit 1
    fi
done
```

## Testing Strategy

### Unit Tests

Unit тесты будут проверять отдельные функции скрипта:

1. **Тест `determine_musl_suffix()`**
   - Проверить правильный суффикс для каждой из 8 архитектур
   - Проверить обработку неизвестной архитектуры

2. **Тест `construct_sdk_url()`**
   - Проверить формат URL для разных версий OpenWrt
   - Проверить корректность имени файла

3. **Тест обработки ошибок**
   - Проверить вывод при отсутствии переменных окружения
   - Проверить вывод при ошибке 404
   - Проверить вывод при ошибке верификации

### Property-Based Tests

Property-based тесты будут использовать **bats** (Bash Automated Testing System) для тестирования скрипта.

Каждый property-based тест должен:
- Запускаться минимум 100 итераций
- Использовать случайные комбинации входных данных
- Проверять универсальные свойства

**Библиотека для PBT:** bats-core с bats-support и bats-assert

### Integration Tests

Integration тесты будут проверять полный цикл сборки Docker образа:

1. **Тест сборки образа для каждой архитектуры**
   - Запустить `docker build` для каждой из 8 архитектур
   - Проверить успешное завершение
   - Проверить наличие SDK в образе

2. **Тест размера образа**
   - Проверить, что размер образа не превышает 2GB

3. **Тест содержимого образа**
   - Проверить наличие `/opt/openwrt-sdk`
   - Проверить наличие необходимых инструментов (make, gcc, git)

## Implementation Notes

### Определение суффикса MUSL

Текущая логика в скрипте:
```bash
MUSL_SUFFIX="_musl"
if [ "${SDK_TARGET}" = "ipq40xx" ] || [ "${SDK_TARGET}" = "ipq806x" ]; then
    MUSL_SUFFIX="_musl_eabi"
fi
```

Эта логика корректна для текущих 8 архитектур, но может потребовать обновления при добавлении новых архитектур.

### Версия GCC

Текущая версия GCC в OpenWrt 23.05.5 - это 12.3.0. При обновлении версии OpenWrt может потребоваться обновление версии GCC в скрипте.

### Curl опции

Рекомендуемые опции для curl:
- `-f` - fail on HTTP errors
- `-L` - follow redirects
- `--retry 15` - retry up to 15 times
- `--retry-delay 10` - wait 10s between retries
- `--retry-all-errors` - retry on all errors, not just transient
- `--max-time 3600` - maximum time for operation (1 hour)
- `--connect-timeout 60` - connection timeout
- `--speed-limit 1000` - minimum speed (1KB/s)
- `--speed-time 30` - time to maintain minimum speed
- `-C -` - continue interrupted download

### Диагностика 404 ошибок

При ошибке 404 скрипт должен:
1. Вывести полный URL, который не найден
2. Попытаться получить список файлов в директории:
```bash
curl -s "https://downloads.openwrt.org/releases/${OPENWRT_VERSION}/targets/${SDK_TARGET}/${SDK_SUBTARGET}/" | \
    grep -oP 'openwrt-sdk-[^"]+\.tar\.xz' | sort
```
3. Предложить пользователю проверить правильность параметров

## Security Considerations

1. **Верификация контрольных сумм**
   - Всегда проверять SHA256 сумму скачанного файла
   - Использовать HTTPS для загрузки файлов и контрольных сумм

2. **Безопасность переменных окружения**
   - Валидировать входные параметры
   - Не допускать injection через переменные окружения

3. **Безопасность Docker образа**
   - Использовать официальный Ubuntu образ
   - Удалять временные файлы после установки
   - Минимизировать количество установленных пакетов

## Performance Considerations

1. **Размер образа**
   - Использовать multi-stage build для минимизации размера
   - Удалять кеши apt и временные файлы
   - Целевой размер: < 2GB

2. **Время сборки**
   - Использовать кеширование Docker layers
   - Параллельная сборка для разных архитектур (max-parallel: 4)

3. **Сетевая производительность**
   - Использовать CDN OpenWrt для быстрой загрузки
   - Продолжение прерванных загрузок
   - Разумные таймауты и retry

## Deployment Strategy

1. **Тестирование**
   - Запустить unit тесты локально
   - Запустить integration тесты в CI
   - Проверить сборку для всех 8 архитектур

2. **Развертывание**
   - Создать feature branch
   - Обновить скрипт `download-sdk.sh`
   - Запустить workflow `build-sdk-images.yml` вручную
   - Проверить успешную сборку всех образов
   - Создать PR и смержить в main

3. **Мониторинг**
   - Проверить логи сборки в GitHub Actions
   - Проверить размеры образов в GHCR
   - Проверить использование образов в CI workflow

## Future Enhancements

1. **Автоматическое определение версии GCC**
   - Парсить страницу OpenWrt для определения актуальной версии GCC

2. **Поддержка других версий OpenWrt**
   - Добавить поддержку OpenWrt 22.03.x
   - Добавить поддержку snapshot builds

3. **Кеширование SDK**
   - Использовать GitHub Actions cache для SDK файлов
   - Уменьшить время сборки при повторных запусках

4. **Валидация образов**
   - Автоматическая проверка работоспособности SDK в образе
   - Тестовая сборка простого пакета
